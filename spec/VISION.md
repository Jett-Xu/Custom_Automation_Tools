# VISION — 這個專案要變成什麼

- **狀態：** 定稿 v2（此文件描述目標，不描述做法）
- **與 SPEC 的關係：** SPEC-00…12 是實現本文的手段。本文不隨 SPEC 改版。
- **用途：** 紀錄。當實作走偏、或要判斷某個新需求該不該做時，回來對照這份。

---

## 1. 一句話

一個跑在自己機器上的**個人開發 harness** —— 我先想清楚要做什麼並寫成一份
SPEC，然後在手機上把那份 SPEC 丟給它；它拆成任務、每個任務派一個 AI agent
去改真實 repo、再派另一個 agent 驗證，過程全程留痕可回查。通訊軟體與 AI
供應商都是可抽換的插槽。

---

## 2. 分工 —— 這是整個設計的前提

| 誰 | 做什麼 | 在哪 |
|----|--------|------|
| **人** | 想清楚要做什麼。被 grill 逼問、釐清模糊處、寫下可檢查的驗收標準 | 筆電，離線，用 grill-with-docs → to-spec |
| **Harness** | 照著做，並確認做到了。拆任務、派工、驗證、留痕 | 本機服務，從手機驅動 |
| **接點** | 一次核准 —— 看到具體計畫後點頭或修正 | 聊天室 |

**我保留唯一機器做不好的部分（釐清意圖），交出去的都是機器做得比人穩的部分
（不會漏掉某條 FR、不會跳過驗證、不會謊報完成）。**

這個分工帶來一個結構性的好處：任務的驗收標準是**我寫的**、被 grill 逼問過的、
可檢查的 —— 不是 LLM 從模糊需求反推出來的。整個驗證環節的價值建立在這件事上。

---

## 3. 核心流程 —— 一則訊息的完整生命

輸入長這樣（丟的是**路徑**，不是內容 —— 一份 SPEC 貼不進聊天室）：

```
@myapp 實作 spec/SPEC-09-run-store.md
@myapp 實作 spec/SPEC-09-run-store.md 的 FR-09-1 到 FR-09-3
```

| # | 階段 | 內容 |
|---|------|------|
| 1 | **收訊息** | Telegram／Discord／Line 皆可。只有白名單裡的人能用 |
| 2 | **分流** | 閒聊？問答？產文件？還是工程任務？**大多數訊息在這裡就結束了，不該花錢** |
| 3 | **讀 SPEC** | 依 alias ＋ 路徑讀取，限制在該專案內。內容與 sha256 存成快照 —— 之後每一步都用快照，不重讀磁碟 |
| 4 | **拆任務（to-tickets）** | SPEC 的每條 FR 對應一個任務。**驗收標準逐字抄自我寫的「驗收：」**，抄不到才讓 AI 補寫（並標記出來）。條目太多就切批，不是失敗 |
| 5 | **等我點頭** | 計畫送回聊天室，含 SPEC 檔名與 sha、每個任務對應的 FR 編號、AI 補寫的驗收標記、成本預估。回「執行」才動；回意見就重新拆；不回就逾時取消。**這關無法用設定跳過** |
| 6 | **執行** | 拓撲排序，能平行就平行（有上限）。每個任務 ＝ 一個 agent CLI 子進程，跑在自己的 git worktree 裡。依賴傳遞的是**檔案狀態**，不是文字 |
| 7 | **驗證（任務級）** | 先跑目標專案自己的 `npm run check`（客觀事實），再交給**另一個** agent 對照該 FR 的驗收標準判定 |
| 8 | **重試** | 被駁回就帶著具體理由重跑，上限 2 次。逾時的不重試 |
| 9 | **驗證（需求級）** | 全部跑完後再驗一次：對照 SPEC 快照問「這份的每一條都被實作了嗎」。有缺口就列出來，狀態是 `done_with_gaps` 而不是 `done` |
| 10 | **整併回報** | 通過的合併到 `harness/<runId>/result` 分支（不碰我的分支、絕不 push）。逐任務回報 passed／unverified／failed／skipped |
| 11 | **留痕** | 全程進 SQLite。事後一道指令拿到完整報告：SPEC 快照、核准的計畫、每個任務的每次嘗試、每個驗證結論、每份產物 |

## 4. 兩個插槽

**通訊軟體** —— 加一個 Line 等於：寫一個 transport adapter ＋ registry 一行。
編排層完全不知道訊息從哪來。

**AI 供應商** —— 加一個 Codex 等於：寫一個 agent adapter ＋ registry 一行
＋ 一組契約測試。編排層完全不知道背後是哪個 CLI，也不出現任何 CLI 名稱或 flag。

這兩件事是本專案存在的理由之一。任何讓「編排層知道供應商細節」的設計，
無論多方便，都是錯的。

---

## 5. 五條不可退讓的線

1. **動真實檔案前一定有人類關卡。** 計畫必須經我核准才執行。這不是設定項。
2. **驗收標準優先來自 SPEC 原文。** AI 補寫的必須被標記出來，讓我知道哪些
   是猜的。
3. **每個 agent 都在隔離的工作目錄，且逾時／卡住一定被殺掉整棵進程樹。**
   關機時也一樣 —— 不留殭屍、不留卡在 `running` 的 run。
4. **部分成功永遠如實回報。** 不存在把「10 條 FR 做完 8 條」講成完成的路徑。
   任務全過但需求沒滿足，也要說出來。
5. **`git push` 不出現在 codebase 任何地方。** 推送永遠是人的決定。

## 6. 明確不做的

| 不做 | 理由 |
|------|------|
| **需求釐清 / grill** | 在 harness 之外由人完成。harness 的輸入是已經想清楚的 SPEC |
| 自建 agent loop | 委派給既有 CLI。自己做工具定義／權限／context 管理沒有勝算 |
| 自動續跑中斷的 run | agent 對檔案系統的修改不冪等。標記中斷、保留 worktree，由人決定重不重來 |
| 跨 run 的記憶／對話上下文 | 每個 run 獨立。要接續就寫進下一份 SPEC |
| 自動解衝突 | 衝突就停下來，把 worktree 路徑交出去 |
| 多實例／分散式 | 單進程、單使用者。所有設計都建立在這個前提上 |
| 幫人做決定 | 缺資訊時回問（一問一答，不迴圈），不猜 |

## 7. 怎樣算做到了

以下每一條都要能當場示範，不是「架構上支援」：

- [ ] 手機上發「@myapp 實作 spec/SPEC-09-run-store.md」，收到一份 10 個任務、
      每個標著對應 FR 編號的計畫，回「執行」後真的動工，最後收到逐任務狀態的
      報告。
- [ ] 計畫裡的驗收標準，跟我 SPEC 裡寫的「**驗收：**」逐字相同。
- [ ] 發「早安」不會花任何一毛錢，也不會建 run。
- [ ] 把驗證者從 Claude 換成別的 CLI，改一行設定就生效。
- [ ] 加一個 Line bot，編排層一行程式碼都不用改。
- [ ] 執行到一半按 Ctrl-C，所有 agent 子進程在 5 秒內消失，沒有殘留，
      run 被標記為中斷並通知我。
- [ ] 一週後回頭問「上次那個 FR-09-3 為什麼失敗」，一道指令拿到答案，
      含驗證 agent 寫下的具體理由。
- [ ] 計畫漏掉了某條 FR 時，我一眼就看得出來（因為每個任務都標著 FR 編號）。
- [ ] 10 個任務全部通過，但 SPEC 裡有一條沒被實作 → 報告說「有缺口」，
      不說「完成」。
- [ ] 這個 harness 的 SPEC-01…12 本身，可以當它自己的輸入。

## 9. 已知的執行風險（不是設計缺口）

1. **四個技術假設尚未驗證** —— CLI 的非互動模式是否穩定、agent 是否願意寫
   `result.json`、第二個 CLI 是否有可用的 headless 模式、worktree ＋ merge
   對 agent 產生的改動順不順。任一為假，SPEC-09/10/11/12 都要改。
   **對策：先做 spike，不要先做 SPEC-01。**
2. **implement 類 playbook 要重寫** —— 舊的 15 份 prompt 是寫給「回一段文字」
   的模型看的，不是寫給「有工具、在 repo 裡工作」的 agent。plan 類的可以直接
   搬，implement 類的是重寫。（已知並接受）
3. **實作量** —— 約 120 條需求。底盤（階段 1–5）做完時還看不到想要的東西，
   要到階段 8 才第一次跑通。這是最大的耗竭風險。
